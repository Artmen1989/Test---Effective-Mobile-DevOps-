# Архитектура отправки PUSH-уведомлений в мобильном приложении «Петрушка Зеленая»

## Верхнеуровневая схема (блок-схема)
[Мобильное приложение] ──(регистрация device token)──► [API Gateway / User Service]
│ │
│ сохраняет token в БД
│ │
│◄─────────────── PUSH-уведомление ──────────────────────────────│
│ │
│ [Сервис уведомлений]
│ ▲
│ │
│ (событие: корзина, заказ, реклама)
│ │
│ [Брокер сообщений]
│ (Kafka / RabbitMQ) ▲
│ │
│ ┌───────────────────────┴────────────┐
│ │ │
│ [Сервис корзины] [Сервис заказов]
│ (таймер бездействия) (статус отмены)
│
│ [CRM / Маркетинг] ──(рекламные кампании)


## Компоненты и их взаимодействие

1. **Мобильное приложение**  
   - При первом запуске запрашивает разрешение на push.  
   - Получает `device_token` от FCM (Firebase) / APNS (iOS).  
   - Отправляет токен на бэкенд вместе с `user_id` и типом устройства.

2. **API Gateway + User Service**  
   - Принимает регистрацию токена.  
   - Хранит в БД `(user_id, device_token, platform, last_active)`.

3. **Сервис-источники событий** (микросервисы)  
   - **Сервис корзины** – отслеживает таймаут бездействия (например, через 30 минут после последнего изменения).  
   - **Сервис заказов** – генерирует событие «заказ отменён».  
   - **CRM / Маркетинг** – периодически (или по расписанию) создаёт рекламные кампании с целевой аудиторией.

4. **Брокер сообщений** (Kafka / RabbitMQ)  
   - Принимает события: `cart_abandoned`, `order_cancelled`, `marketing_push`.  
   - Обеспечивает асинхронную доставку до Сервиса уведомлений.

5. **Сервис уведомлений**  
   - Подписан на топики брокера.  
   - По `user_id` получает из User Service актуальные `device_token` и платформу.  
   - Формирует payload (заголовок, тело, data-поля).  
   - Отправляет запрос к FCM/APNS через соответствующие SDK.  
   - Логирует результат отправки (успех / ошибка / невалидный токен).  

6. **База данных User Service**  
   - Таблицы: `users`, `push_tokens`, `push_preferences` (опционально).  
   - ER-диаграмма (упрощённо):
users (id PK, phone, email)
push_tokens (id PK, user_id FK, token, platform, created_at, last_used)
push_preferences (user_id PK, allow_cart, allow_orders, allow_marketing)


## Поток данных на примере «корзина слишком долго без действий»

1. Сервис корзины при каждом обновлении корзины обновляет `last_activity` в своей БД.  
2. Фоновый воркер (или Kafka Streams) раз в минуту сканирует корзины, у которых `now() - last_activity > 30 минут`.  
3. По каждой такой корзине отправляется событие `cart_abandoned` с `user_id` в Kafka.  
4. Сервис уведомлений читает событие, запрашивает токены для `user_id`.  
5. Отправляет push: «Ваша корзина ждёт вас! Оформите заказ сейчас».  

## Вопросы для обсуждения на собеседовании

- Как обрабатывать миллионы пользователей? – очереди, шардирование токенов, rate limiting у FCM/APNS.  
- Что делать с невалидными токенами? – удалять из БД.  
- Как гарантировать доставку? – retry с exponential backoff, dead-letter queue.  
- Как реализовать A/B-тесты для рекламных пушей? – отдельный сервис экспериментов.  
- Отличие микросервисной архитектуры от монолита – здесь каждый сервис независим.  
- Работа REST API vs HTTP – в схеме используется внутренний HTTP/gRPC между сервисами и брокером.
